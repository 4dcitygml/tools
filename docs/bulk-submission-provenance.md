# Bulk submissions: provenance, verification, and merge policy

**Status: policy v1 (2026-09).** This document fixes *what a bulk submission
must contain* and *how it is verified*. For the identity kinds the gates are
implemented in this repository (`scripts/commit_building_scope.py`,
`scripts/identity_manifest.py`, `scripts/source_update_manifest.py`,
`scripts/fetch_materials.py`, CI gate `reproduction`); they still have to be exercised on a real repository during the
private pilot before the identity PR types are unlocked
([PR operations guide §7.2](https://github.com/4dcitygml/city-template/blob/main/docs/pr-operations.md)).
For `source-update`, value replacements within one attribute family are
implemented (§4.2); edition changes are handled by `carry-forward` (§4.3),
not by converting old files. Documentation never substitutes for an unimplemented gate.

## 1. Scope

A *bulk submission* is a PR whose data commits were **generated by a
program** from a declared source, rather than edited building by building:

| PR type | What it does | Change-Type trailer |
|---|---|---|
| `source-baseline` | records an official dataset unchanged | `source-baseline` (already gated) |
| `scope-extract` | removes buildings outside the municipality | `scope-extract` (already gated: CI re-runs the extraction and byte-compares) |
| `source-update` | applies an official annual edition, one building per commit | per-building trailers |
| `identity-baseline` | unifies historical `uro:buildingID` values to the current edition, one building per commit | `identity-baseline` (gated; pilot pending) |
| `identity-correction` | fixes a mis-linked ID in published history | `identity-correction` (gated; pilot pending) |
| `carry-forward` | re-bases the repository's accumulated changes onto a new official edition (three-way merge per building and semantic attribute; the edition change itself) | per-building trailers + `Carry-Forward-From:` |
| `schema-update` | adds an edition's artifacts (code lists, schema profile); no GML change | `schema-update` (gated: artifact paths only) |
| `schema-migration` | when the repository is the master and no official new-edition file exists: generates the new edition's serialization from the repository's content (registry-driven re-serialization of the i-UR subtree; CityGML 3.0 core via 3DCityDB) | `schema-migration` (designed; gate = semantic equality per registry key + reproduction, not yet implemented) |
| `layout` | semantics-preserving mesh subdivision | `layout` |

Everyday single-building corrections are **not** bulk submissions and keep
the normal flow (one PR, human review of the building).

## 2. Principle: verify by reproduction, not by reading

Reviewing thousands of generated per-building commits by eye is neither
feasible nor meaningful. Bulk submissions are therefore accepted on the same
basis as generated code, reproducible builds, and dataset imports elsewhere:

- **CI reproduces the result.** The submission declares its inputs (with
  digests), the exact tool version, and the exact invocation. CI fetches the
  inputs, verifies the digests, re-runs the tool at that version, and
  byte-compares the outcome with the PR. Any difference blocks the merge.
- **Humans review the plan, the manifest, and a sample** — never the
  individual buildings. The manifest lists what was linked or changed, with
  the numeric evidence per building, and what was deliberately left alone.
- **No bypass.** "Trusted submitter" is expressed through ownership and
  required checks, not through rule bypasses: the provenance paths are owned
  by the city's maintainers in CODEOWNERS, their review is required, and the
  author may not approve their own PR.
- **Revertible unit = PR = one mesh.** Reverting the merge commit restores
  exactly one mesh; nothing else moves.

This mirrors established practice: CI `verify-*` jobs that regenerate
generated files (Kubernetes, Go), Reproducible Builds `.buildinfo` and
SLSA/in-toto provenance (declare materials, builder, invocation; verify by
independent re-execution), the OpenStreetMap import guidelines and automated
edits code of conduct (plan first, dedicated account, revertible chunks,
tagged changes), and bot-driven migrations in package ecosystems
(conda-forge, nixpkgs: humans review the migration definition and CI results,
not each diff).

## 3. What a submitter provides

Every bulk PR MUST contain all of the following. Items 1–4 are checked by
machine; 5–6 by the city's maintainers.

1. **A plan issue, opened before the PR** (Part B of the exchange contract).
   It states scope (city, meshes, editions), sources (URLs), the tool and
   version to be used, the order of PRs, and the expected counts. The PR body
   links it (`Plan-Issue:`).
2. **A provenance manifest file committed in the PR**, at
   `provenance/<kind>/<mesh>-<edition_from>-<edition_to>.json`, conforming to
   [`schemas/provenance/bulk-manifest.schema.json`](../schemas/provenance/bulk-manifest.schema.json)
   (example: [`docs/examples/bulk-manifest.example.json`](examples/bulk-manifest.example.json)).
   Its vocabulary follows SLSA/in-toto provenance:
   - `materials` — every input with `uri`, `sha256`, `bytes`, and for ZIP
     members the member `path` + `sha256` (so CI can fetch by HTTP Range);
   - `builder` — `tools_repo` and the **immutable commit SHA** of
     `4dcitygml/tools` used (never a branch or a moving tag), plus the script;
   - `invocation` — the exact command line and parameters, and the runtime
     versions (Python, lxml, shapely…);
   - `products` — every produced file in the PR with its `sha256` and
     building count;
   - `evidence` — the per-building decisions. For `identity-baseline`: the
     per-boundary *ID regime* (`continuous` / `mixed` / `renumbered`, from
     the measured share of same-ID pairs that are geometrically consistent),
     the thresholds used, every link (`from`, `to`, `tier`, `method`, `iou`,
     `centroid_m`, `hausdorff_m`, `area_ratio`, `competitor_iou`, `chain`),
     and every building deliberately **not** linked with its reason. For
     `source-update`: the allowed attribute paths, old/new values, and the
     target ID set (the existing `History-Manifest` fields).
3. **Commit trailers on every data commit** (exchange contract A2), plus
   `Provenance-Manifest: <path>@sha256:<hex>` pointing at the manifest file,
   and `Created-By: <tool>/<version>` naming the generator. `identity-*`
   commits carry `Building-ID-From:` / `Building-ID-To:` and
   `Identity-Evidence: tier=…;method=…;iou=…;centroid_m=…;chain=…`.
4. **PR body fields** in the template's "Source / manifest" section:
   `Source-From`, `Source-To`, `Scope-Mesh`, `Provenance-Manifest`,
   `Manifest-SHA256`, `Building-Count`, `Plan-Issue`, and the reason section
   (`<!--sec:reason-->`) stating in one paragraph what was generated and why.
5. **A dedicated submitting account.** Bulk PRs are opened by a conversion
   account (or a GitHub App), not by a maintainer's personal account, so that
   human edits and machine conversions are separable in the audit trail. The
   account is named in the plan issue.
6. **A sample-audit record.** The manifest's `sample_audit` block fixes a
   random seed and sample size (default 30 buildings per mesh, or all if
   fewer); the reviewer inspects those buildings in the viewer / diff and
   records the result in the PR. Ambiguous cases (tier C in an identity
   manifest) are listed by the submitter and confirmed or rejected one by one
   by the reviewer; they are never auto-linked.

A human-readable report MAY be attached, but it is derived from the manifest
and is not a merge condition.

## 4. How CI verifies (the reproduction gate)

1. Manifest present, schema-valid, `sha256` equals the value in every
   commit's `Provenance-Manifest:` trailer and in the PR body.
2. `builder.tools_commit` is an immutable SHA that exists in `4dcitygml/tools`
   (or in the mirror named by the repository variable `CITYGML_TOOLS_REPO`).
3. Every material is fetched (ZIP members by HTTP Range) and its digest
   matches.
4. The invocation is re-executed at that tools commit; the products are
   byte-compared with the PR head. For `identity-baseline`, the regenerated
   `evidence` block must equal the committed one (canonical JSON), every
   commit's `From`/`To` pair must appear in `evidence.links` with tier A or B,
   `To` must not exist anywhere else in the repository at the parent commit,
   and `To` must exist in the declared current edition.
5. The existing per-commit gates keep running (one change = one building,
   trailer consistency, schema, structure, plausibility); their comments are
   summarized by count for bulk PRs.
6. Required approvals: a CODEOWNERS review of `provenance/` by the city's
   maintainers; the author cannot approve; stale reviews are dismissed on
   push.

Only when every item passes is the PR mergeable. Merge method: merge commit
(rule 5 of the PR operations guide), one mesh per PR.

### 4.1 Implementation (identity kinds)

- **Generate**: `python3 scripts/identity_manifest.py generate --mesh … --municipality …
  --edition 2020=… --edition 2022=… … --edition-uri 2020=<zip-url>#<member-path> …
  --product <repo path of the baseline GML> --tools-commit <sha> --plan-issue <url>
  --output provenance/identity-baseline/<mesh>-<from>-<to>.json`. The tool
  classifies each boundary's ID regime, tiers every link with geometric
  evidence, composes the chain, defers links whose target ID is still held
  by a retained building (tier C, re-attempt after that building is removed
  by the annual update), orders the links so that one-commit-at-a-time
  application never creates a duplicate ID, and records the sample audit.
- **Commits**: `identity_manifest.py commits --repo <clone> --manifest <path>`
  writes one commit per link with the A2/A7 trailers.
- **Gate (commit scope)**: for every identity commit — exactly one
  `Building-ID-From`/`To`, the building's bytes unchanged apart from the ID
  value, Appearance unchanged, the manifest present with the trailer's
  digest, the pair listed in `evidence.links` with tier A or B (tier C only
  when the PR carries the `identity-review` label), the target ID absent
  from every GML file of the repository at the moment the commit applies,
  and an `identity-baseline` PR applying every link of its manifest.
- **Gate (reproduction)**: `fetch_materials.py` re-fetches the
  declared materials (ZIP members by HTTP Range, digests verified) and
  `identity_manifest.py verify --materials-dir …` regenerates the manifest;
  materials, evidence and products must match canonically.
- Bulk PRs get count-only commit-scope output and no per-building
  reviewability lint or 3D preview (they would exceed the comment limit).

### 4.2 Implementation (source-update, one attribute family)

- **Generate**: `python3 scripts/source_update_manifest.py generate --mesh … --municipality …
  --family storeys --current <repository GML at the parent commit> --current-label 2024
  --edition-new 2025=<official GML> --product <repo path> --tools-commit <sha> --plan-issue <url>
  --output provenance/source-update/<mesh>-2024-2025-storeys.json`. Targets are
  the buildings whose `uro:buildingID` exists on both sides; a change is a
  modified leaf value at a path of the family, replaced in place
  (byte-preserving). Leaves that are added or removed by the new edition, or
  whose tag/value is ambiguous inside the building, are listed under
  `evidence.excluded` with a reason and are **not** applied: such edition
  restructurings are handled by `carry-forward` (§4.3).
- **Commits**: one `Building: <id>` commit per target with `Attribute-Family:`,
  `Source-To:` and `Provenance-Manifest:` trailers.
- **Gate (commit scope)**: one manifest per PR, every changed building among
  the manifest's targets exactly once, the building's bytes equal to the
  parent's bytes with the manifest's changes applied, all targets applied.
- **Gate (reproduction)**: as for identity — materials re-fetched (the current
  file via `git:<sha>:<path>`), manifest regenerated and compared.

### 4.3 Implementation (carry-forward: edition change)

- **Generate**: `python3 scripts/carry_forward_manifest.py generate --mesh … --municipality …
  --base <previous official edition> --current <repository file> --new <new official edition>
  --product <repo path> …`. Per building and semantic key
  ([registry](semantic-registry.md)) the tool compares the previous official
  value, the repository value and the new official value: a change that only
  we made is **reapplied** on the new file; a change the new edition already
  carries is recorded as **absorbed**; different changes on both sides are a
  **conflict** for human decision; a key the new edition does not have is
  **unmappable** (held); a key whose leaf the new building lacks is
  **insert-needed** (held). Attributes split by the edition change distribute
  the single value to each successor present. Coded attributes are mapped
  through the edition pair's code-list crosswalk; a code without a 1:1
  mapping is **carried with the old edition's codeSpace** (recorded under
  `evidence.carried_old_codespace`) instead of being lost or forced.
- **City rules**: the shared crosswalk is merged with the city's reviewed
  rules (`--overrides semantics/overrides.json`, same shape, confidence
  `reviewed`); a reviewed rule with a single target is applied automatically.
  The overrides file's digest is recorded in the manifest.
- **Product and commits**: the new official file is recorded unchanged as the
  next `source-baseline`; when codes are carried, the old edition's code lists
  are committed first under `codelists/<edition>/` (`commits --codelists-from`);
  the reapplied values follow as one `Building:` commit per building
  (`Carry-Forward-From:` trailer), gated exactly like `source-update` (§4.2),
  and the `reproduction` gate regenerates the manifest from the three
  materials. `scripts/carried_codespace_report.py` counts what is still
  carried before an official export.

## 5. Merge and rollback

- Merge with a merge commit; the PR is the rollback unit.
- After merge, the manifest stays in the repository as the permanent record
  of that conversion; Git history plus the manifest is the source of truth
  (no separate ledger).
- If a link is later found to be wrong, open an `identity-correction` PR
  (same package, plus `Corrects: <sha>` naming the commit being corrected).
  Published history is never rewritten.

## 6. Relation to other documents

- `scripts/building_history.py` — the per-building timeline derived from git
  and the manifests (community proposals as commits, official editions as
  baselines with manifest classifications), so traceability per building does
  not depend on commit granularity. `--index-out` builds the static Pages
  index a city repository publishes with its `history-index.yml` workflow.

- [Semantic attribute registry](semantic-registry.md) — edition-independent
  attribute keys and their paths per i-UR edition; the basis for carrying
  changes across an edition change.

- Exchange contract A2/A7 — trailer names and the bulk clause.
- PR operations guide §4.3–4.4, §7.2 — PR types, checklists, and the gate
  implementation status.
- Provenance rules — how sources are recorded *inside* the data (i-UR
  quality attributes); this document covers the provenance of the
  *conversion*.
